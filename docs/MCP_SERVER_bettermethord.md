一、检索层：让 Schema 过滤更精准

  1. 引入混合检索（Hybrid Search）

  当前只用了向量检索（KNN），但向量检索对精确匹配不友好。比如用户说"查询 CPU
  使用率"，cpu 这个关键词可能被语义相近但不相关的表干扰。

  方案：向量检索 + BM25 关键词检索结合，对两种检索结果做融合排序（如 RRF — Reciprocal
  Rank Fusion）。Redis 本身支持全文索引，可以在同一索引中同时做向量和文本检索。

  2. 检索粒度从表级下沉到列级

  当前是检索"相关的表"，但对于宽表（几十上百列），LLM 仍然面临列选择的困难。

  方案：对列的描述也建立向量索引，检索时同时返回相关表和相关列。构建 Sub-Schema
  时只包含最相关的列，进一步压缩 prompt 并提升精度。

  3. 增加重排序（Re-Ranking）

  当前用 Embedding 的余弦相似度直接做阈值过滤，但双塔模型的区分度有限。

  方案：在粗召回 top_k 表后，用一个 Cross-Encoder 模型（如
  BAAI/bge-reranker-v2-m3）对候选表做精排。Cross-Encoder 能同时看到 query 和 table
  description 的交互，区分度远好于双塔。

  4. 优化知识库中表的描述文本

  当前 Redis 中存储的 description
  字段决定了检索质量的上限。如果描述只是表名，检索效果会很差。

  方案：为每张表生成高质量描述，包含：
  - 表的中文业务含义
  - 主要字段和用途
  - 典型查询场景

  甚至可以反过来用 LLM 自动生成这些描述。

  ---
  二、生成层：让 SQL 更准确

  5. 动态 Few-Shot 示例选择

  当前是 Zero-Shot 直接生成 SQL。如果 LLM 能参考相似问题及其正确
  SQL，精度会显著提升，这是 Text-to-SQL 领域被广泛验证的方法。

  方案：
  - 维护一个历史查询-SQL 对的知识库（人工审核过的正确 SQL）
  - 用户查询来时，用向量检索找到最相似的 2-3 个历史示例
  - 拼接到 prompt 中作为 few-shot 示例

  【相似问题示例】
  问题：查询sundb_metrics库sys_cpu_usage表最近1小时的平均CPU使用率
  SQL：SELECT AVG(value) FROM sundb_metrics.sys_cpu_usage WHERE ts > NOW() - INTERVAL
  '1 hour'

  问题：查询abortspanbytes表中HOST_IP为172.19.19.111的前10条数据
  SQL：SELECT * FROM sundb_metrics.abortspanbytes WHERE HOST_IP = '172.19.19.111'
  LIMIT 10

  6. 显式引入 Schema Linking 步骤

  当前直接让 LLM "根据 Schema 生成 SQL"，但经验表明，让 LLM 先显式找出相关列，再生成
  SQL，效果更好（DIN-SQL、DAIL-SQL 等论文的核心思想）。

  方案：两阶段生成：
  - Step 1：让 LLM 从 Sub-Schema 中选出与问题相关的表和列
  - Step 2：基于选出的列生成 SQL

  # Step 1 prompt
  "根据用户问题，从以下 Schema 中找出相关的表和列，以 JSON 格式返回"

  # Step 2 prompt
  "根据用户问题和以下相关列信息，生成正确的 SQL"

  7. 多候选 SQL + 自投票（Self-Consistency）

  对于同一个问题，让 LLM 生成多条 SQL（temperature > 0），然后投票选出最优。

  方案：生成 3-5 条候选 SQL → 执行 → 比较执行结果的一致性 → 选出最合理的结果。如果多个
   SQL 结果一致，可信度更高；如果不一致，标记为需要人工确认。

  8. 执行前自检（Self-Correction before Execution）

  当前是执行失败后才修复。可以在执行前让 LLM 自检。

  方案：生成 SQL 后，追加一个自检 prompt："请检查以下 SQL
  是否存在语法或逻辑错误，如有问题请修正"。这会捕获一部分明显的错误。

  ---
  三、纠错层：让修复更智能

  9. 结果反馈闭环

  当前修复循环只处理 SQL 语法/执行错误，但不处理逻辑错误（SQL 能执行但结果不对）。

  方案：在修复循环中增加结果分析：
  - 空结果检查：如果结果为空，提示 LLM 检查 WHERE 条件是否过严、时间范围是否合理
  - 异常结果检查：如果返回行数异常多（接近截断上限），提示可能需要加 LIMIT 或聚合
  - Schema 示例值校验：如果 WHERE 条件的值与列的示例值格式不一致，提示可能的错误

  if len(results) == 0:
      feedback = "查询返回了空结果。请检查：1) WHERE 条件是否过于严格 2)
  时间范围是否正确 3) 字符串值是否精确匹配"
      # 用这个 feedback 作为修复 prompt 的一部分

  10. 错误模式学习

  当前每次修复都是独立的，没有积累经验。

  方案：将修复成功的 (错误信息, 原SQL, 修复后SQL)
  记录到数据库，后续遇到相似错误时，直接检索历史修复案例作为 few-shot 参考。

  ---
  四、数据层：让上下文更丰富

  11. 列的值分布概览

  当前列的 Schema 信息只包含 5 个 distinct 示例值，但 LLM 不知道列的值域范围。

  方案：在 Schema 中为数值列增加 MIN/MAX/AVG，为字符串列增加 常见值 top5 +
  唯一值数量，为时间列增加 最小/最大时间。这让 LLM 生成 WHERE 条件时更有依据。

  字段: cpu_usage (FLOAT64)
    示例值: [23.5, 45.1, 67.8, 12.3, 89.0]
    取值范围: [0.0 - 100.0]  ← 新增
    常见值: [45.1, 23.5, 67.8]

  12. 表间关系显式化

  当前 M-Schema 包含外键信息，但 prompt 中可能没有强调表之间的 JOIN 关系。

  方案：在 Schema 展示中增加一个 "常见 JOIN 关系" 部分，描述表之间如何关联：

  常见关联：
  - sundb_metrics.sys_cpu_usage.host_id ↔ sundb_metrics.host_info.host_id
  - 典型的查询会 JOIN host_info 获取主机的 IP 地址和名称
