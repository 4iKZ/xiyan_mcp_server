# 表名缩减方案方法论

## 1. 背景

GreptimeDB 中存储了 2,344 张 CockroachDB Prometheus 指标表，共计 12,643 个字段，平均每表 5.4 个字段。直接将全部表名喂给 NL2SQL 模型（XiYanSQL-QwenCoder-32B，上下文窗口 32K tokens）是不可行的。即使仅包含表名不含任何 Schema 详情，2,344 张表的格式化文本占约 50,000 tokens，远超上下文窗口上限。

因此需要合理缩减，在保证查询覆盖的前提下将表数量控制在上下文窗口容量之内。

## 2. 缩减策略：双源交叉验证

我们采用双源交叉验证策略，从两个独立来源收集"有用表"集合，取并集作为最终候选集。

### 2.1 数据源

**源 A：NL2SQL 数据集人工标注**

数据集 `cockroach_nl2sql_1500.jsonl` 包含 1,500 条自然语言查询，每条查询附带人工标注的目标表（`tables` 字段）和标准 SQL（`sql` 字段）。从这两个字段中提取所有被引用的表名，去重得到 242 张表。这些表覆盖了 Level 1 到 Level 5 所有难度层级的基础查询需求。

**源 B：模型实验的二级筛选输出**

使用 XiYanSQL-QwenCoder-32B 模型，在 stage2 精筛开启、stage1 向量粗召回 N=40、stage2 模型精筛 M=5 的配比下，对全部 1,500 条查询进行了 NL2SQL 实验（1,262 条成功生成并执行）。实验过程记录在 `query_tracker_2026-06-27_merged_s2on_n40_m5_32b_1500_noise0.jsonl` 中。

二级筛选流程如下：
1. **Stage 1（向量粗召回）**：使用 Qwen3-Embedding-8B 对用户查询与 2,344 张表的知识库描述（`embedding_content`，平均 160 字符，包含表名、名称、技术描述和业务含义）进行向量相似度检索，取 Top-40 候选表。
2. **Stage 2（模型精筛）**：将 40 张候选表及其知识库描述提交给 Qwen3-32B 精筛模型，由模型从中选出最相关的 5 张表（`stage2_tables`），用于构建子 Schema 并生成 SQL。

从实验记录的 `stage2_tables` 字段中，提取所有被精筛模型选中的表名，去重得到 891 张表。

### 2.2 合并与去重

```
源 A（数据集标注）: 242 张
源 B（模型 stage2 精筛）: 891 张
─────────────────────────────
交集（两源共同确认）: 242 张
仅源 B（模型发现、数据集未标注）: 647 张
仅源 A（数据集标注、模型未选中）: 0 张
─────────────────────────────
合并去重: 889 张
```

值得注意的是，数据集的 242 张表全部包含在 stage2 的 891 张输出中（交集 100%），说明人工标注的表模型均能通过向量检索+精筛流程覆盖到。额外的 647 张表是模型在实验中自行发现的关联表，主要出现在 Level 4/5 的多表 JOIN 和复杂诊断查询中。

### 2.3 元数据表排除

从合并结果中排除了 4 张非业务指标的元数据表：
- `node_id`：节点标识元数据
- `build_timestamp`：构建时间戳
- `target_info`：监控目标信息
- `greptime_physical_table`：GreptimeDB 内部物理表

## 3. Stage 2 选表频次分布

891 张 stage2 选中的表中，出现频次分布如下：

| 出现频次 | 表数量 | 说明 |
|---------|--------|------|
| >= 10 次 | 268 | 高频核心表，覆盖主要查询场景 |
| >= 5 次 | 418 | 中高频表 |
| == 1 次 | 244 | 边缘表，仅在少数查询中被模型选中 |

高频表前五名：
1. `sys_cpu_combined_percent_normalized`（56 次）— CPU 综合利用率
2. `rpc_connection_unhealthy`（56 次）— RPC 连接健康检测
3. `security_certificate_expiration_client_tenant`（54 次）— 证书过期检测
4. `sql_service_latency_bucket`（54 次）— SQL 服务延迟分布
5. `sql_service_latency_count`（50 次）— SQL 服务延迟采样数

## 4. 最终结果

| 指标 | 数值 |
|------|------|
| GreptimeDB 原始表数 | 2,344 |
| 缩减后表数 | 889 |
| 缩减比例 | 62.1% |
| 所有表验证通过（在 DB Schema 中存在） | ✓ |
| 重复表 | 0 |
| 遗漏的数据集标注表 | 0 |

## 5. 上下文窗口验证

使用 XiYanSQL-QwenCoder-32B 的实际 Tokenizer（实测 4.22 字符/token），对 32K tokens 上下文窗口进行容量验证：

| 模式 | 字符数 | Token 数 | 上下文占比 |
|------|--------|---------|-----------|
| 仅表名（889 张） | 57,679 | 13,668 | 42% |
| 表名 + KB 描述 | ~191,000 | ~45,500 | 139%（超出） |

仅表名模式下，889 张表占用上下文窗口的 42%，留有 58% 的充裕空间用于系统提示词、用户问题及模型生成的 SQL。若需要携带知识库描述，则可进一步筛选至约 500 张（高频核心表），仍能在 32K 窗口内容纳。
